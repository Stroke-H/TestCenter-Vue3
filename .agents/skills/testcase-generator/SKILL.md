# 测试用例生成器 (Test Case Generator)

## 概述

本 Skill 用于根据给定的功能需求或接口描述，自动生成结构化的测试用例。**所有测试场景必须完整覆盖以下四大维度**，缺一不可：


| 维度      | 英文标识          | 说明                            |
| ------- | ------------- | ----------------------------- |
| ✅ 正向场景  | `POSITIVE`    | 验证功能在合法、预期输入下的正确行为            |
| ❌ 逆向场景  | `NEGATIVE`    | 验证功能在非法、边界、不合规输入下的拒绝/容错行为     |
| ⚠️ 异常场景 | `EXCEPTION`   | 验证功能在系统异常（网络中断、服务宕机、超时等）下的健壮性 |
| 🔄 并发场景 | `CONCURRENCY` | 验证功能在高并发、竞态条件下的数据一致性与稳定性      |


---

## 核心规则

> [!CAUTION]
> 以下规则为强制约束，生成用例时必须严格遵守，不得跳过任何维度。

### 规则 1：四维全覆盖原则

每一个测试场景（Feature / API / Module）都 **必须** 包含正向、逆向、异常、并发四类用例。如果某个维度确实不适用，必须在用例文档中 **显式声明原因**，而非静默忽略。

### 规则 2：用例结构标准化

每条用例必须包含以下字段：

```markdown
| 字段 | 说明 | 必填 |
|------|------|------|
| 用例ID | 唯一标识，格式: `TC-{模块缩写}-{场景类型}-{序号}` | ✅ |
| 场景类型 | `POSITIVE` / `NEGATIVE` / `EXCEPTION` / `CONCURRENCY` | ✅ |
| 用例标题 | 简洁描述测试目的 | ✅ |
| 前置条件 | 执行用例前需满足的条件 | ✅ |
| 测试步骤 | 具体操作步骤，编号列出 | ✅ |
| 测试数据 | 输入数据及参数 | ✅ |
| 预期结果 | 明确的、可验证的期望输出 | ✅ |
| 优先级 | `P0`(阻塞) / `P1`(核心) / `P2`(重要) / `P3`(一般) | ✅ |
| 备注 | 补充说明、关联缺陷、特殊环境要求等 | 可选 |
```

### 规则 3：用例 ID 命名规范

格式: `TC-{MODULE}-{TYPE}-{SEQ}`

- `MODULE`: 模块缩写，如 `LOGIN`, `PAY`, `ORDER`
- `TYPE`: 场景类型缩写
  - `P` = POSITIVE（正向）
  - `N` = NEGATIVE（逆向）
  - `E` = EXCEPTION（异常）
  - `C` = CONCURRENCY（并发）
- `SEQ`: 三位数序号，从 `001` 开始

示例: `TC-LOGIN-P-001`, `TC-PAY-E-003`, `TC-ORDER-C-002`

### 规则 4：客户端聚焦原则 (Client-Side Focus)

当需求涉及 **AB 测试** 或 **三方支付** 等外部/中心化平台功能时，必须严格区分测试主次：

- **仅测试客户端行为**：重点验证 App 端的 UI 展示切换、本地状态变更、接口回调处理及异常提示。
- **忽略平台侧功能**：不考虑 AB 测试平台服务端自身的逻辑（如分流算法准确性、管理后台配置功能）或三方支付机构内部的结算逻辑。
- **目的**：确保测试用例聚焦于“被测 APP 的表现”，避免用例冗余。

## 各场景类型设计指南

### ✅ 正向场景 (POSITIVE)

目标：验证系统在 **正常、合法** 条件下的功能正确性。

**设计要点：**

- 使用合法的、符合规范的输入数据
- 覆盖所有主流程路径（Happy Path）
- 覆盖不同合法参数组合
- 验证返回值/状态/副作用均符合预期
- 包括首次操作和重复操作的验证

**示例模板：**

```
用例ID: TC-LOGIN-P-001
场景类型: POSITIVE
用例标题: 使用正确的用户名和密码登录
前置条件: 用户已注册且账号状态正常
测试步骤:
  1. 打开登录页面
  2. 输入已注册的用户名
  3. 输入正确密码
  4. 点击登录按钮
测试数据: 用户名=testuser01, 密码=Test@12345
预期结果: 登录成功，跳转至首页，显示用户昵称
优先级: P0
```

### ❌ 逆向场景 (NEGATIVE)

目标：验证系统在 **非法、边界** 条件下的拒绝与容错能力。

**设计要点：**

- 空值 / Null / 未定义输入
- 超长字符串、特殊字符、SQL 注入、XSS 攻击向量
- 边界值（最小值-1、最大值+1、零值）
- 类型错误（字符串传入数字字段等）
- 权限不足的操作
- 已过期/已失效的凭证或数据
- 重复提交/幂等性验证

**示例模板：**

```
用例ID: TC-LOGIN-N-001
场景类型: NEGATIVE
用例标题: 使用错误密码登录
前置条件: 用户已注册且账号状态正常
测试步骤:
  1. 打开登录页面
  2. 输入已注册的用户名
  3. 输入错误密码
  4. 点击登录按钮
测试数据: 用户名=testuser01, 密码=WrongPass123
预期结果: 登录失败，提示"用户名或密码错误"，不跳转，登录失败计数+1
优先级: P0
```

### ⚠️ 异常场景 (EXCEPTION)

目标：验证系统在 **非预期的系统级故障** 下的健壮性和恢复能力。

**设计要点：**

- 网络中断 / 超时 / 高延迟
- 数据库连接失败 / 读写异常
- 第三方服务不可用 / 返回异常
- 磁盘空间不足 / 内存溢出
- 服务重启 / 进程崩溃后的恢复
- 消息队列积压 / 消费失败
- 配置缺失 / 环境变量异常

**示例模板：**

```
用例ID: TC-LOGIN-E-001
场景类型: EXCEPTION
用例标题: 登录时后端服务不可用
前置条件: 认证服务已停止
测试步骤:
  1. 打开登录页面
  2. 输入正确的用户名和密码
  3. 点击登录按钮
测试数据: 用户名=testuser01, 密码=Test@12345
预期结果: 页面显示"服务暂不可用，请稍后重试"，不出现白屏或未捕获异常
优先级: P1
```

### 🔄 并发场景 (CONCURRENCY)

目标：验证系统在 **多用户/多线程/高并发** 条件下的数据一致性和稳定性。

**设计要点：**

- 多用户同时操作同一资源（读写冲突）
- 同一用户多端/多窗口同时操作
- 秒杀/抢购等高并发业务场景
- 分布式锁的有效性验证
- 数据库死锁检测与恢复
- 消息顺序性和幂等性
- 连接池耗尽场景
- 限流与降级策略验证

**示例模板：**

```
用例ID: TC-ORDER-C-001
场景类型: CONCURRENCY
用例标题: 100 个用户同时抢购最后 1 件库存
前置条件: 商品库存 = 1，100 个用户已登录
测试步骤:
  1. 准备 100 个并发请求
  2. 同时发送下单请求
  3. 检查订单创建结果
  4. 检查库存最终值
测试数据: 商品ID=SKU001, 库存=1, 并发数=100
预期结果: 仅 1 个订单创建成功，库存=0，其余 99 个请求返回"库存不足"，无超卖
优先级: P0
```

## 使用方式

### 输入

向 Agent 提供以下信息之一：

1. **功能需求文档**：PRD / 用户故事 / 功能描述
2. **API 接口文档**：接口地址、请求参数、响应格式
3. **简要描述**：用自然语言描述要测试的功能

### 输出

Agent 将生成包含四大维度的完整测试用例集，格式为 Markdown 表格或结构化文档。

### 调用示例

```
请根据以下需求生成测试用例：

功能：用户注册
- 用户输入手机号、验证码、密码完成注册
- 手机号需要是有效的 11 位中国手机号
- 验证码 5 分钟内有效
- 密码需要 8-20 位，包含大小写字母和数字
```

## 质量检查清单

生成用例后，请使用以下清单自检：

- 是否覆盖了 **正向场景**？（至少 3 条核心正向用例）
- 是否覆盖了 **逆向场景**？（至少 5 条边界/异常输入用例）
- 是否覆盖了 **异常场景**？（至少 2 条系统级异常用例）
- 是否覆盖了 **并发场景**？（至少 1 条并发竞态用例）
- 用例 ID 是否规范且唯一？
- 每条用例的预期结果是否 **明确且可验证**？
- 优先级标注是否合理？
- 是否存在冗余/重复用例？

---

## 输出格式选项

Agent 支持以下输出格式（默认 Markdown）：

1. **Markdown 表格** — 适合文档归档和 Wiki 发布
2. **JSON 结构** — 适合导入测试管理平台
3. **YAML 结构** — 适合版本控制和 CI/CD 集成
4. **Excel 兼容 CSV** — 适合传统测试管理
